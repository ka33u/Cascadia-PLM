2026-09-15。已完成从迁移`0005_cad_model_node_links`到`0010_npi_bom_drafts`的隔离自动化演练；使用仓库原始迁移文件，未修改迁移SQL。

## 数据与结果

测试先用0000～0005建立升级前数据库，再写入原生业务夹具，最后执行NPI迁移。与“先建全量新库再造NPI数据”的恢复测试不同，本测试在升级前已有原生对象。

升级前84张业务表，共18行合成数据：3名用户、2个项目（在研/完成）、2条项目成员权限、4个原生Item、2个父子Task、1个Issue、1个Document、1条问题/资料关联、1份Vault文件记录和1条设置。实际文件含中文原始字节。空表也纳入逐表摘要，不能把84表误解为84张表都有数据。

4项测试通过：

1. 在临时迁移副本的最后一步注入异常：0006～0010的新增表及迁移记录一起回滚，旧数据、列定义、约束保持原样。
2. 执行未经修改的正式迁移：旧表全部逐行内容、列定义、约束一致；父子任务、问题到资料到文件的关系、采购成员只读标记及文件字节保持原样。
3. 重复执行全部迁移：数据和迁移记录不增加、不改变。
4. 升级后新增NPI项目，导入前导零BOM、设置重点件、添加外购物料、采购和制造回复，得到正确瓶颈和明细/管理承诺冲突；旧业务行仍存在且字节表示未变。

PostgreSQL：16.13（Homebrew）。本次随机隔离数据库已由测试成功删除，验证日志和临时文件夹具保留在测试输出路径。没有迁移运行库，也没有修改已有`_test`数据库。机器记录见本目录`upgrade-verification.json`。

## 复现

从独立系统根目录执行：

```sh
TSX_TSCONFIG_PATH=packages/core/tsconfig.json node --env-file=.env --import tsx scripts/npi-upgrade.test.ts
```

必须配置指向本机、名称以`_test`结尾的`TEST_DATABASE_URL`，连接账号需有创建数据库权限。脚本只借用其服务器连接信息，创建本次独有的`cascadia_npi_upgrade_<随机值>_test`数据库；不会迁移该配置指向的数据库。退出时只删除本次已成功创建的数据库，不使用强制终止其他会话或覆盖现有数据库。

测试输出四个PASS结果和临时验证目录；任何失败都不能据此宣称升级通过。异常注入只改临时迁移副本，仓库迁移SQL不变。

## 验证边界

这是给定旧版schema和合成原生业务数据的兼容性验证，已经补齐自动化旧库升级路径的证据。不是用户真实企业数据库的克隆，不证明未知定制schema、历史脏数据、额外触发器、跨PostgreSQL主版本或生产规模升级均可通过。

正式旧库升级前仍需独立备份、核对实际迁移位置和自定义结构，在隔离副本复演并逐表/逐文件验收；生产停机与恢复方案另行确定。本轮未更改应用功能或迁移文件，所以不重复全量前端构建和浏览器套件；新增测试已通过类型及静态检查。
